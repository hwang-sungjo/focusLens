> 이 문서는 이후 백엔드 작업의 진행 기준이다. Phase 1부터 Phase 5까지 순서대로 진행하고, 완료 조건을 충족한 항목만 `[✅]`로 변경한다.

## 0. 작업 범위

### 수정 대상

- `backend/`: Express API, 인증, 컨트롤러, 서비스, 운영 설정
- `prisma/`: 스키마, 마이그레이션, View, 시드
- `src/**/*.test.js`: 현재 Jest 설정이 사용하는 백엔드 테스트
- `docker-compose.yml`, 백엔드 배포·CI 설정
- `docs/`: 백엔드 API, ERD, 보안, 운영 문서

### 수정하지 않는 대상

- `ai/`: Python, MediaPipe, 카메라, 점수 계산, API 클라이언트를 포함한 전체 디렉터리
- `frontend/`: 제품 프런트엔드 구현

AI와 프런트엔드는 외부 클라이언트로 취급한다. Phase 4에서는 현재 요청 형식을 고정한 fixture와 HTTP 요청으로 백엔드 계약을 검증한다. 실제 카메라, AI 재시도, 브라우저 화면 E2E는 백엔드 완료 조건에 포함하지 않는다.

### 백엔드가 수신하는 현재 로그 형식

v1은 기존 AI 클라이언트 호환용이다.

```json
{
  "gaze": 85.5,
  "blink": 72.0,
  "head": 90.0,
  "total": 79.65,
  "face_detected": true
}
```

- v1 `logged_at`과 분 구간은 서버의 세션 시작 시각과 수신 시각으로 결정한다.

신규 연동은 v2를 사용한다.

```json
{
  "client_log_id": "123e4567-e89b-42d3-a456-426614174000",
  "measured_at": "2026-10-08T06:01:00.000Z",
  "gaze": 85.5,
  "blink": 72.0,
  "head": 90.0,
  "total": 79.65,
  "face_detected": true
}
```

- v2는 `measured_at`으로 원래 분 구간을 계산한다.
- `(session_id, client_log_id)`와 `(session_id, minute_index)` UNIQUE 제약으로 재전송을 판정한다.
- v1과 v2 구현 계약은 `docs/api-spec.md`, 클라이언트 규칙은 `docs/client-contract-decisions.md`를 따른다.

### 가중치 변경 후속 정합성 점검 (2026-10-14)

이번 수정 범위는 백엔드 코드, `src/**/*.test.js`의 백엔드 테스트, 백엔드 문서다. 기존 `ai/` 작업본은 유지하며 AI·프런트엔드 파일을 추가 수정하지 않는다.

- [✅] 가중치 `gaze × 0.3 + blink × 0.5 + head × 0.2`, 세부 점수와 요청 total의 소수 둘째 자리 정규화, 서버 계산값 저장 기준 확인
- [✅] 백엔드 테스트의 요청·DB 모의 데이터·응답 기대값 수정, v1·v2의 새 합산값 저장과 이전 합산값 400 거부 검증
- [✅] API·계획·클라이언트 계약 문서 예시와 Swagger의 가중치·예시 정리
- [✅] 문서 정리 후 전체 Jest, OpenAPI 대조, 문서 예시 산술 정합성 검증과 최종 기록

> 테스트 단계 완료: `(80, 70, 90)`의 합산값을 77, `(85.55, 72.22, 90.11)`의 반올림 결과를 79.80으로 맞췄다. 정규화 테스트의 63.34점 모의 데이터·응답 상태를 `NORMAL`로 수정하고 실제 INSERT 인자에서도 상태를 확인했다. 관련 Jest 2 suite·35 test와 백엔드 전체 13 suite·90 test가 통과했다. 실제 DB·HTTP 연동 테스트는 이번 단계에서 실행하지 않았다.

> 문서·최종 검증 완료: `(85.5, 72.0, 90.0)` 로그의 요청·응답·타임라인 예시를 79.65로 맞추고 같은 세션의 종료·목록·상세·리포트·공유 피드 평균 예시를 77.57로 통일했다. Swagger v1·v2에 정상·얼굴 미검출 요청과 정상 응답 예시를 추가하고 세부 점수·요청 total 정규화와 서버 계산값 저장 순서를 명시했다. API·계획·클라이언트 계약 문서의 JSON 예시 62개 파싱, Markdown·Swagger 가중치 계산 예시 13개와 로그 응답 4개 검증, 백엔드 Jest 13 suite·90 test, OpenAPI 38 operation 대조를 통과했다. 문서의 timeline은 전체 로그 중 첫 로그만 보여주는 축약 예시임을 명시했다. 기존 DB 점수 변경과 실제 DB·HTTP·카메라·브라우저 E2E는 실행하지 않았다.

외부 대기 항목: AI 테스트 기대값 갱신과 Python 검증, AI의 정규화·반올림·실제 전송값 검증, 카메라 1분 집계·로그 v2 전송 연결, 프런트 점수 표시 E2E. 기존 DB 점수 재계산은 별도의 백엔드 데이터 변경 정책 작업이며 이번 범위에 포함하지 않는다.

### AI-1 로그 v2 수신 검증 (2026-11-24)

- [✅] 테스트 계정으로 로그인한 뒤 실제 HTTP로 세션 시작 → 로그 v2 전송·재전송 → 종료 → 리포트 조회까지 통과했다. 격리된 PostgreSQL 16에 마이그레이션 11개와 조회 View를 적용하고 Redis 7에 연결했다.

| 측정 구간 | 입력 (gaze, blink, head) | 얼굴 검출 | API 응답 | DB 저장 점수 | 리포트 타임라인 | 판정 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| 1분 | 85.5, 72, 90 | true | 79.65 | 79.65 | 79.65 | FOCUSED |
| 2분 | 0, 0, 0 | false | 0 | 0 | 0 | DISTRACTED |

각 구간을 같은 `client_log_id`·`measured_at`으로 두 번 보냈다. 네 요청이 모두 200을 반환했고 재전송은 최초 응답과 같았다. DB에는 두 행이 남았고 종료 요약·저장된 리포트·조회한 리포트의 평균은 모두 **39.83**이었다(집중 1분, 이탈 1분). 실제 실행의 세션 ID는 `71291f04-be8c-4fdc-bcdc-7fb5db1f1e6c`, 리포트 ID는 `aae59ed6-b7df-474d-a0f2-35e8383d02a6`이다.

**재실행** — Node.js 20 이상과 Docker Compose v2(`up --wait` 지원)가 필요하다. 처음에는 저장소 루트에서 `npm ci --prefix backend`로 의존성을 설치하고, 이후 `npm run verify:ai1`을 실행한다. 실행마다 별도 컨테이너와 루프백 임시 포트를 할당하고 종료 시 정리한다. 성공하면 세션·리포트 ID와 비교 결과를 JSON으로 출력한다.

이 검증은 고정 입력 두 건을 사용하며 방금 만든 테스트 세션의 시작 시각만 125초 앞당겨 두 분 구간을 재현한다. 다음 AI-2에서 실제 카메라의 1분 집계·전송을 검증한다.

### AI-2 실제 카메라 1분 로그

- [✅] 2026-11-24 실제 카메라 자리 비움 검증. 60초간 509개 샘플 중 얼굴 검출 0개. 로그 v2 HTTP 200, DB 1행, 세션 종료·리포트 HTTP 200. API·저장값·리포트 평균 모두 0점이었으며 타임라인의 판정은 `DISTRACTED`였다. 세션 `2b5f8a66-84c7-4af1-902a-1dcf48a106e0`, 리포트 `0732a7f0-13de-4f2a-a182-ff6485825eb7`.
- [✅] 실제 카메라로 얼굴이 검출된 별도 60초 구간(498/498)에서 자리 비움용 0점 로그 전송이 차단됐다.
- [✅] 얼굴 검출 구간의 보정·깜빡임 집계와 실제 양수 점수 저장·리포트 대조. 2026-11-24 보정 표본 23개, 이후 60초 유효 샘플 504개(모두 얼굴 검출). 시선 86.11, 눈 감김 100, 자세 100, 총점 95.83이 API·DB·종료 요약·저장 리포트·조회 타임라인에서 일치했다. 세션 `8b587d86-3119-4203-bec2-d7f745b190cc`, 리포트 `1a78c5ab-2e50-4f09-a990-35574993a0ae`.

자리 비움 검증은 백엔드 검증 도구에서 기존 Python `WebcamPipeline`과 MediaPipe 얼굴 검출기를 호출한다. 첫 측정 프레임부터 60초를 집계하고, 구간 끝의 단조 시각을 UTC로 변환해 v2의 `measured_at`에 담는다. 480개 이상 샘플에서 얼굴 검출률이 80% 미만일 때만 네 점수 0과 `face_detected=false`를 보내고, DB 한 행·세션 종료 요약·리포트 타임라인을 비교한다. 장치 영상은 메모리에서 처리한다.

- **실제 카메라** — AI-1의 실행 환경에 [AI 의존성](../ai/README.md)과 Python 3.11을 준비하고, 카메라가 빈 곳을 보도록 한 뒤 저장소 루트에서 `npm run verify:ai2:absence`를 실행한다. `AI2_PYTHON`으로 가상환경의 Python 경로, `AI2_CAMERA_INDEX`로 장치 번호(기본 0), `FOCUSLENS_MODEL_PATH`로 모델 경로를 지정할 수 있다.
- **카메라 없는 재현** — 같은 환경에서 `npm run verify:ai2:absence:fixture`를 실행한다. 검은 이미지를 10 FPS의 가상 시각으로 실제 검출기에 전달한다. 첫 분 600개 샘플, 얼굴 0개에서 API·DB·리포트가 모두 0점으로 일치했다. 출력의 `source`가 `blank-fixture`이면 합성 입력, `camera`이면 실측이다.
- **정상 얼굴 실측** — 같은 환경에서 `npm run verify:ai2:focus`를 실행한다. 처음 3초는 화면 중앙을 정면으로 바라보고, 이후 60초는 평소처럼 화면을 본다. 보정 표본 최소 20개와 측정 표본 최소 480개를 확보한 뒤 API·DB·리포트의 점수·상태·시각·행 수를 비교한다. 실측 세션 시작 시각은 유지한다.
- **눈 감김 감점 재현** — `npm run verify:ai2:focus:fixture`는 합성 feature 600개를 집계한다. 감김 시간 13.8초(23%), 1초 이상 연속 감김 1회에서 `100-20-8=72`점, 시선 85.5·자세 90과 합산한 79.65점이 API·DB·리포트에서 일치했다. 최종 재실행 세션 `ec759c5a-0a77-4c6d-b254-7d28f38d4b9e`, 리포트 `91b2703b-fdc1-44e1-9c10-404be77ff92a`. 이 재현에서는 테스트 세션 시작을 65초 소급한다.
- **확정 계산 기준** — 2026-11-24 요청에 따라 양눈 감김값이 각각 0.8 이상인 시간을 60초로 나눈다. 비율 15%부터 장시간 눈 감김으로 표시하고, 15%를 초과하는 완전한 1%p당 1점을 추가 감점한다(16%→1점, 23%→8점). 1초 이상 연속 감김은 1회당 20점을 함께 감점하며 0~100으로 제한한다.
- **관측 누락** — 10 FPS 입력에서 프레임 간격이 250ms를 넘거나 얼굴·눈 측정값이 누락되면 감김 연속성을 끊고 그 시간을 `unknown_blink_ms`에 기록한다. 정상 실측에서 이 값은 1,002ms였다.

연동 집계는 기존 feature 모델·카메라·설정·가중 계산 함수를 재사용하는 `backend/scripts/ai2_scoring.py`에 구현했다. AI-2의 재현 단위는 실제 카메라 한 분의 생성→v2 전송→DB→종료 리포트까지다. 다음 AI-3에서 지속 세션의 오프라인 큐·토큰 갱신·종료 전 대기 로그 처리를 검증한다.

검증 기록 — 통합 도구 Python unittest 17개, 기존 AI pytest 9개, 백엔드 Jest 90개, OpenAPI 38개 operation 대조가 통과했다. 시선 좌표가 일시적으로 누락되어도 눈 감김값이 유효하면 감김 시간을 집계하며, 480개 미만의 유효 표본은 전송하지 않는다.

### AI-3 큐·토큰 갱신·세션 종료 검증 (2026-11-25)

- [✅] `backend/scripts/ai3_delivery.py`에 SQLite 영속 전송 큐를 구현했다. 로그를 먼저 기록한 뒤 전송하고, 성공 응답을 확인하면 완료 처리한다. 프로세스 재시작 후에도 `client_log_id`·`measured_at`·점수를 보존한다.
- [✅] 네트워크 오류·408·429·500/502/503/504에서 최대 8회 재시도하고 이후에도 대기 로그를 보관한다. 429의 `Retry-After`를 우선하고, 나머지는 1/2/4/8/16/30초 상한의 full jitter를 적용한다.
- [✅] 만료된 Access Token의 401에서 Refresh Token을 회전하고 원 요청을 한 번 다시 보냈다. Refresh 503 후 복구와 재사용 토큰 family 폐기도 실제 API·DB로 확인했다.
- [✅] Refresh 응답 유실·토큰 저장 실패·갱신 중 프로세스 종료에 대비해 요청 전 토큰의 SHA-256 지문을 기록한다. 같은 이전 Refresh Token의 재전송을 막고 재인증을 요구한다.
- [✅] 대기 또는 실패 로그가 있으면 종료 API를 보내지 않는다. 400/403/404/409는 자동 재시도를 중단하고, 복구 불가능 로그는 호출자가 사유를 기록해 명시적으로 제외한 뒤 종료할 수 있다. 종료 응답이 유실되면 완료된 세션·리포트를 조회해 복구한다.
- [✅] macOS 키체인 어댑터의 일회용 항목 저장·조회·교체·삭제를 확인했다. 토큰은 프로세스 인자로 전달하지 않으며 큐 파일에는 보관하지 않는다.

**실제 HTTP 검증 결과** — 격리된 PostgreSQL 16·Redis 7과 임시 프록시에서 오프라인 503, 429, 로그·Refresh·종료 응답 유실을 재현했다. 큐가 남은 프로세스를 종료한 뒤 별도 worker에서 복구했다. 세 로그가 원래 1·2·3분에 한 건씩 저장됐고 점수 `[79.65, 0, 77]`, 평균 **52.22**가 종료 요약·DB 리포트·조회 타임라인에서 일치했다. 최종 재실행 세션 `7cade471-2090-4dd6-89b7-30eac5133657`, 리포트 `b8a8b011-5666-46ef-b3f0-2d0b983554e2`.

재실행은 AI-1의 Docker 환경과 Python 3.11의 `httpx`를 준비한 뒤 `AI3_PYTHON=/가상환경/bin/python npm run verify:ai3`로 한다. 검증에서는 테스트 세션의 시작 시각을 245초 앞당겨 세 개의 완료 분 구간을 만들고, 재시도 대기를 테스트용 함수로 단축하며, 1시간 대기 대신 서명된 만료 JWT를 사용한다. HTTP·PostgreSQL·Redis·SQLite는 실제 경로로 실행한다. 검증 계정의 토큰은 메모리에서만 사용하며 키체인 검증은 별도의 일회용 항목으로 수행했다.

최종 점검 — 통합 도구 unittest **37개**(AI-2 17개, 전송 17개, 키체인 3개), 기존 AI pytest 9개, 백엔드 Jest 90개, OpenAPI 38개 operation 대조가 통과했다. 같은 UUID의 대소문자 및 `Z`·`.000Z` 표기 차이는 같은 응답으로 인정하며, 원본 큐 payload는 유지한다.

**연결 모듈 사용** — 로그인 응답은 `KeychainTokens(user_id).set(access_token, refresh_token)`으로 저장하고, 같은 계정에는 고정된 outbox 파일 경로 하나를 사용한다. `DeliveryClient(base_url, queue_path, token_store)`의 `enqueue(session_id, payload)`로 AI-2의 완성 로그를 기록하고 `drain(session_id)`으로 전송한다. 측정을 멈춘 뒤 `finish_session(session_id)`을 호출하면 기존 대기 로그를 처리한 후 종료한다. 종료를 요청한 큐에는 새 측정 로그를 추가할 수 없다. 같은 큐를 두 worker가 동시에 열면 소유권 잠금으로 차단한다.

### LBE-3 완료 기록 (2026-11-25)

Redis의 3회 재시도 후 영구 단절되는 설정을 최대 2초 간격의 지속 재연결로 변경했다. 오프라인 큐를 끄고 명령 제한을 1.5초로 두어 장애 중 인증 요청을 나중에 재실행하지 않는다. 연결은 서버 실행 시 시작하므로 OpenAPI 검사처럼 앱을 읽기만 하는 도구는 Redis에 접속하지 않는다. DB 연결 단절·시간 초과는 503으로 표준화하고 명세에 반영했다.

- [✅] `npm run verify:recovery`로 별도 PostgreSQL 16·Redis 7·최신 API를 기동했다. 검증 전용 세션만 70초 소급해 v2 로그 79.65점과 종료 리포트를 만들었다.
- [✅] Redis를 6초 이상 중지한 동안 Health·보호 조회·로그아웃 503을 확인했다. 같은 볼륨으로 Redis를 재기동하자 API 컨테이너·프로세스를 재시작하지 않고 복구했고, 이전 로그아웃 토큰은 계속 401이었다.
- [✅] PostgreSQL 중지 동안 Health·DB 기반 조회 503을 확인했다. DB 재기동 후 같은 API 프로세스에서 기존 점수·리포트 응답이 일치했다. 이 재현의 장애 요청 최대 응답 시간은 Redis 5ms·DB 8ms였고 검증 요청 제한은 8초였다.
- [✅] API를 먼저 중지한 유지보수 상태에서 검증용 Redis를 초기화하고 `local:recover-auth`를 실행했다. 과거 정상·로그아웃 Access Token과 과거 Refresh Token이 401이 되었고, 기존 활성 Refresh Token이 모두 폐기됐다. 새 로그인 후 기존 79.65점 리포트는 그대로 조회됐다.
- [✅] SIGINT·SIGTERM 시 HTTP 신규 접수와 Roll-up 예약을 중단하고, 진행 중 작업 완료 후 Prisma·Redis를 정리하도록 구현했다. 정상 상태와 DB·Redis 단절 상태에서 컨테이너 종료 코드 0, 네 자원의 종료 로그를 확인했다. stop·상태 확인은 각각 307ms·315ms였다.
- [✅] 기본 8초 종료 제한, 진행 중 요청·Roll-up 대기, 중복 신호, Redis quit 실패 대체 정리, 정리 실패·시간 초과 강제 종료를 단위 테스트로 검증했다.
- [✅] Jest 16 suite·116 test, 인증 복구 명령의 실패·취소·경합·설정 보존 테스트 17개, 기존 환경 파일 테스트 6개, OpenAPI 38개 operation 및 구문·공백 검사를 통과했다. 검증 전용 컨테이너·볼륨·이미지·임시 파일을 정리했다.
- [✅] 일반 로컬 서버도 최신 이미지로 갱신하고 `localhost:3000`의 Health·기존 계정·세션·리포트 조회 200을 확인했다. 전체 21개 테이블의 행 수·해시와 기존 환경 파일이 갱신 전후 같았다(계정 17개·세션 12개·리포트 12개·로그 6개). 원본 서버에는 장애나 인증 초기화를 적용하지 않았다.

일반 서버 갱신 전 백업은 `backups/focuslens-2026-11-25T10-22-55-467Z-7f1c3b1d-4ec2-4c2c-89d6-1b9d3c15e020.dump`에 보관했다(93,992 bytes, SHA-256 `b59908cd7d633dcbf00a4d3c8fa1058e56a2603fc9b5118c7e88388409c49cfb`).

Redis 데이터 유실 복구는 **API 중지 → JWT 비밀값 교체 → 모든 Refresh Token 폐기 → API 재생성** 절차다. 실패 시 API 중지 상태를 유지한다. 실행 중 예고 없는 `FLUSHDB`의 자동 감지·차단을 제공하는 것은 아니므로 Redis 초기화·교체·유실 복구 전에 API부터 중지한다. 명령·잠금·실패 시 조치는 [장애 복구 운영 절차](performance-operations.md#7-로컬-장애-복구와-종료)를 따른다. 다음 단위는 LBE-4 지속 AI 연결이다.

로컬 작업 완료 후 프런트엔드 통합으로 진행한다. AWS·RDS·ElastiCache·클라우드 Secret·외부 HTTPS·자동 배포·CloudWatch 구성은 배포 재개 시 Phase 5에서 진행한다.
